# Starter Code Review — Employee Attendance & Analytics API

This review identifies defects in the original `app/main.py` starter code. The starter's basic happy path was present, but several calculations, validations, database operations, and API requirements needed correction.

| # | Location | What was wrong | How it was identified | Fix in the implementation |
|---:|---|---|---|---|
| 1 | `compute_late_minutes()` | The grace-period logic calculated whole minutes first and then checked whether the result was greater than 10. For example, a punch-in at `09:40:01` for a `09:30` shift became 10 minutes and was incorrectly returned as 0. | Checked the exact 10-minute boundary and the first second after it against the required rules. | Apply the grace-period condition to the actual elapsed time, then calculate the required whole late minutes. |
| 2 | `compute_late_minutes()` | The calculation did not explicitly handle the required timestamp normalization and boundary rules. | Tested timestamps at and around the grace-period boundary. | Normalize timestamps according to the API's time-handling rules and apply the specified rounding and grace-period behavior. |
| 3 | `compute_work_hours()` | Python's built-in `round()` uses ties-to-even rounding, which can differ from the required half-up rounding for values exactly halfway between two decimal results. | Compared calculated work hours with the specified two-decimal rounding rule. | Use the required half-up rounding method for work-hour calculations. |
| 4 | `compute_overtime()` | Overtime was calculated against the shift end on the same calendar date. This fails for overnight shifts whose end time belongs to the following day. | Checked shifts where `shift_end` is earlier than or equal to `shift_start`. | Resolve the correct shift-end date for overnight shifts before calculating overtime. |
| 5 | `compute_overtime()` | The helper counted overtime from the shift end without enforcing the required 30-minute minimum. | Compared overtime values below, at, and above the 30-minute threshold. | Return overtime only when the elapsed time meets the specified 30-minute minimum, using whole minutes. |
| 6 | `create_employee()` | Checking for an existing employee before inserting is not enough to prevent duplicate employee codes when concurrent requests arrive. | Reviewed the separate `find_one()` and `insert_one()` operations as a race condition. | Enforce uniqueness with a MongoDB unique index and handle duplicate-key errors as a conflict. |
| 7 | `create_employee()` and `EmployeeIn` | Employee fields were accepted with minimal validation. Invalid dates, shift times, or malformed field values could reach the database. | Compared accepted input fields with the API contract and expected date/time formats. | Validate input formats and values before storing employee records. |
| 8 | `create_employee()` | `datetime.now()` stored a naive timestamp, making the intended timezone unclear. | Inspected how `created_at` was generated and compared it with the API's timestamp requirements. | Store timestamps consistently as UTC datetimes and return them in the required representation. |
| 9 | `list_employees()` | `skip = page * page_size` skipped the first page of records. With page 1 and page size 20, it skipped 20 records instead of 0. | Checked the pagination offset for the first and subsequent pages. | Calculate the offset as `(page - 1) * page_size`. |
| 10 | `list_employees()` | `total` used `count_documents({})`, so it counted every employee even when a department filter was supplied. | Compared the filtered result set with the reported total. | Count using the same filter query used to retrieve the employees. |
| 11 | `list_employees()` and `list_attendance()` | Pagination parameters had no explicit contract-aligned bounds, and employee results had no deterministic sort order. | Tested boundary values and inspected how pages were formed. | Validate page and page-size values and use a stable, deterministic sort order. |
| 12 | `punch_in()` | An unknown `emp_code` could make `emp` equal `None`, followed by `emp["shift_start"]`, causing an unhandled server error. | Traced the request for an employee code that does not exist. | Check employee existence and return the appropriate HTTP error before accessing employee fields. |
| 13 | `punch_in()` | `datetime.fromtimestamp()` and `datetime.now()` depend on the server's local timezone when used without an explicit timezone. The truthiness check also treated a supplied timestamp of `0` as if no timestamp had been supplied. | Inspected timestamp conversion and tested explicit timestamp handling. | Handle missing timestamps separately from supplied values, interpret epoch milliseconds consistently, and normalize timestamps to the required timezone and precision. |
| 14 | `punch_in()` | Checking for an existing attendance record before inserting was vulnerable to concurrent requests creating duplicate records for the same employee and date. | Reviewed the check-then-insert sequence and considered simultaneous punch-in requests. | Enforce the `(emp_code, date)` uniqueness rule with a MongoDB unique index and translate duplicate-key failures into HTTP 409. |
| 15 | `punch_in()` | The starter did not fully enforce the attendance contract for valid employees, allowed status values, attendance-date assignment, and derived values for overnight shifts. | Compared the request handling with the attendance rules and tested boundary cases. | Validate the request, assign the attendance date using the shift rules, and calculate the derived fields using the specified logic. |
| 16 | `list_attendance()` | The endpoint loaded every matching document into Python, sorted the full result set in memory, and only then applied pagination. This can use excessive memory and become slow as the collection grows. | Inspected the query and pagination flow and tested against a large dataset. | Apply filtering, deterministic sorting, skip, and limit in MongoDB; obtain the filtered total separately. |
| 17 | `list_attendance()` | Sorting only by date did not guarantee deterministic order when multiple records had the same date. | Considered records sharing a date and checked pagination stability. | Add a stable tie-breaker to the sort order. |
| 18 | `list_attendance()` and `list_employees()` | The starter did not explicitly validate query parameter bounds and supported values as required by the API contract. | Tested invalid page sizes, page values, dates, and status values against the contract. | Add contract-aligned query validation and return the appropriate validation errors. |
| 19 | Startup/database setup | The starter did not create the required indexes at application startup. | Inspected initialization and verified query plans on the seeded dataset. | Create the required indexes idempotently at startup so repeated application starts do not require manual index creation. |
| 20 | TODO endpoints | The starter did not implement punch-out, attendance regularization, employee monthly analytics, department summary, late leaderboard, department trend, or query-explain endpoints. | Compared the provided routes with `openapi.yaml` and the assignment requirements. | Implement the missing endpoints and their required validation, calculations, audit trail, aggregation pipelines, and explain output. |

## Items inspected and treated as not inherently defective

- `GET /health` returning `{"status": "ok"}` is suitable for a basic health check.
- Using a Pydantic model for employee input is a reasonable starting point; the issue was incomplete validation, not the use of Pydantic.
- Checking for an existing employee or attendance record can provide a useful early error response. It is not, however, a replacement for a database unique constraint when concurrent requests are possible.
- Returning pagination metadata such as `items`, `total`, `page`, and `page_size` is a reasonable response structure. The offset, filtering, validation, and sorting logic needed correction.
